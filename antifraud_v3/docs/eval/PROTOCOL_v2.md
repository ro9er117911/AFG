## 3. Q5：聲學洩漏——本期最重要的一題

### 3.1 為什麼這一題必須做

v1 的獨立審查（`REVIEW_LOG.md` 第 1 項，列為「致命等級」）發現：
論文宣稱「聲學特徵不參與判定」，論據是 `fuse()` 的函式簽章，
但該簽章只證明那個函式不吃聲學參數，不證明聲學不影響使用者看到的判定。

**2026-08-13 複查，洩漏鏈在程式碼中仍然存在**：

| 步驟 | 位置 | 現況 |
|---|---|---|
| 1 | `pipeline/chunk_worker.py` | 建構 `acoustic_summary`（F0、jitter、shimmer、HNR、eGeMAPS） |
| 2 | `reasoning/discriminate.py:10` | `f"聲學特徵：{evidence.acoustic_summary}\n"` 直接進入 LLM prompt |
| 3 | `reasoning/rubric.py:152` | 系統提示明令「引用具體的逐字稿內容**或聲學特徵**作為理由」 |
| 4 | `reasoning/schemas.py` | LLM 輸出 `hard_triggers`（含 `fired: bool`） |
| 5 | `pipeline/call_state.py:247` | `fired_trigger` 可獨立觸發告警，且在 `risk_level` 判斷之前執行 |

`REVIEW_LOG.md` 將此列為**未決——需產品決策**。本協定不做那個決策，
**但先量化它的影響**：決策需要知道代價，目前沒有人知道關掉聲學會不會讓判定變差。

### 3.2 設計

配對設計，同一語料跑兩臂，只有一個變因：

- **A 臂（現況）**：`discriminate()` 的 prompt 含 `acoustic_summary`
- **B 臂（消融）**：同一 prompt，`acoustic_summary` 置換為固定字串 `（未提供）`，
  且 `rubric.py` 的聲學指示段落移除

實作方式：`discriminate()` 增一個 `include_acoustic: bool = True` 參數，
B 臂傳 `False`。**這是評測開關，不是產品行為變更**——預設值不變，
產品路徑不受影響。

### 3.3 判定

| 指標 | 定義 |
|---|---|
| **判定翻轉率** | 兩臂 `risk_level` 不同的通話佔比 |
| **hard-trigger 翻轉率** | 兩臂 `fired_trigger` 有無不同的通話佔比 |
| **配對檢定** | McNemar（配對設計，沿用 v1 REVIEW_LOG 第 4 項的教訓，不比較獨立 CI） |

**事前訂定的解讀規則**（避免事後兩種結果都解釋成好消息）：

| 結果 | 解讀 | 處置 |
|---|---|---|
| 翻轉率 ≈ 0 且 McNemar 不顯著 | 聲學實際上不影響判定 | 可移除洩漏鏈，且**移除的代價為零**——論文原宣稱得以成立 |
| 翻轉率顯著 > 0 且 B 臂較差 | 聲學實際在幫忙 | **不得移除後仍宣稱效能不變**；需在論文明列「本系統的判定確實使用聲學線索」，並承擔 §8 的歷史包袱 |
| 翻轉率顯著 > 0 且 B 臂較好或持平 | 聲學在製造噪音 | 移除，並報告移除後的效能變化 |

三種結果都必須如實報告。**本題刻意不設「通過標準」**——它是事實查明，不是及格考。

### 9.1 §6.2 可行性檢查結果（2026-08-13，執行於任何模型呼叫之前）

**Q5（聲學洩漏）：不予登錄，移至 v3。**

檢查 `eval/teleantifraud.py:281` 發現，Q1 的 harness 直接呼叫
`classify_call_via_llm(provider, text)`（純逐字稿），**完全不經過
`discriminate()`**。已完成的 400 筆 JSONL 欄位為
`['asr_chars','confidence','error','fraud_type','index','label','predicted']`，
**無 `hard_triggers` 欄位**——該路徑在本語料上從未被執行，
A 臂 hard-trigger 觸發率為 0（結構性的 0，非測得的 0）。

依 §6.2 事前訂定的條件「A 臂 hard-trigger 觸發率須 > 0，否則無翻轉空間」，
本題**不予登錄**。

這不是壞消息，而是登錄前檢查發揮了作用：若直接執行，會得到「兩臂判定
100% 一致」的結果，並極易被誤讀為「聲學不影響判定，原宣稱成立」——
但真正的原因是這條語料根本沒有走到那段程式碼。**v1 正是敗在沒做這個檢查。**

Q5 的正確做法需要走完整 `chunk_worker` → `discriminate` → `call_state`
管線的語料（即有音訊分塊與聲學特徵抽取的即時路徑），而非 Q1 的
